Never let the client decide the rules

Addressables & server-authoritative config · architecture · ~7 min read

Two problems that look unrelated — how fast can we ship a change, and can we trust what the player's phone tells us — turn out to have the same answer. It's the decision I'd defend hardest across the titles I work on.

Across Brick Blaster Cash, Cashout Bingo and Blinko, content loads through Unity Addressables, and what loads — along with the values that govern how the game behaves — is decided by configuration that lives on the server. The client asks what the rules are. It does not decide them, and it does not ship with them.

That sounds like ordinary remote config. The difference is in the word authoritative, and it matters more than it sounds.

Problem one: shipping without shipping

A competitive game is tuned continuously. You watch how matches play out, you find that a value is slightly wrong, you change it. On a title where balance is the product, that loop runs constantly.

If those values are compiled into the build, every adjustment costs you a store submission and a review queue. The real cost isn't the waiting. It's that your player base splits: some people have the new build, some have the old one, and in a game where those people compete against each other, they are now playing two subtly different games. That isn't a delay. It's a correctness problem.

Move the values server-side and the loop closes in minutes instead of days, and everybody is playing the same game at the same moment because there is only one source for what the game is.

The same applies to content

Addressables take this past numbers and into assets. Content is not baked into the binary; it is fetched on demand from a catalogue the server points at. New content reaches players without a client release at all — and the install stays small, which matters enormously when your only storefront is the App Store and every megabyte you add costs you installs at the top of the funnel.

Problem two: the phone is not a witness you can trust

Here is the part that changes the architecture rather than just the workflow.

When there is real money on the outcome of a match, every value that influences that outcome is a target. If the client holds the rules — scoring weights, difficulty parameters, what a given action is worth — then the client can be made to lie about them. Not by most players. By enough of them, and that is all it takes: one exploit shared in a forum becomes a payout problem, a fairness problem for everyone who played honestly, and a compliance problem for the business.

The device is never the source of truth about anything that decides a payout.

"Server-authoritative" means the server is not just a convenient place to store values. It is the only place they exist as truth. The client receives them, uses them to render and to play, and is treated throughout as something that might be wrong or hostile. Match results are validated against what the server knows the rules to have been, not against what the client claims they were.

This is the same instinct behind any authoritative multiplayer server. What surprised me is how much of it applies to a game that is, mechanically, single-player. You're not competing in real time against an opponent in Brick Blaster — you're both playing a run and comparing scores. There's no netcode to speak of. And yet the trust model has to be just as strict, because the money is just as real.

Why it's one decision and not two

You could solve these separately. You could use remote config for tuning speed, and bolt on validation for trust. Plenty of games do, and the result is two systems that disagree with each other at the edges — the config the client fetched, and the config the validator believes in. Every disagreement is a bug that surfaces as a wrong payout, which is the worst possible place for a bug to surface.

Making the config authoritative collapses both into one thing. There is a single description of what the game currently is. The client renders it, the validator judges against it, live-ops edits it. No reconciliation, because there's nothing to reconcile.

What it costs

I'd be misrepresenting this if I only listed the wins.

  • The game must survive a bad network. If the rules come from the server, the client needs a sane, well-defined behaviour when the server is slow or unreachable — and "fail open with baked-in defaults" is exactly the hole you were trying to close. This is the hard part and it deserves design attention rather than a fallback constant.
  • Config becomes production. Once a value change reaches players in minutes, a careless edit is an outage. It needs review, history and a way back, the same as code.
  • Addressables are an operational commitment. Catalogues get versioned, assets get orphaned, and a stale catalogue pointed at a missing bundle is a very confusing crash. Convenient at runtime, real work to keep tidy.

Worth it?

For a portfolio of live competitive titles, unquestionably. The tuning loop is the live-ops capability — being able to correct balance the day you notice it rather than the following week is the difference between a healthy competitive game and a slowly rotting one. And the trust property isn't a feature you can retrofit once real money is flowing; it has to be the shape of the thing from the start.

If I were starting a new title tomorrow with money on the outcome, this is the first architectural decision I'd make, before writing a line of gameplay.
